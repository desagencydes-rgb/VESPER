## The four corrections, and what each one returns

### 1. The 24-hour run is not on the critical path, and never was

The build order is fixed by `IMPLEMENTATION_SEQUENCE.md`:

```
F0 → F1 → F2 → F4 → F3 → F6 → F5 → F7 → F8
                              ↑
                        A-029 lives here — 7th of 9
```

`A-029` is **F5's** gate. Perception (F4), presence (F3) and the distributed layer
(F6) all come **before** it. So the endurance run blocks nothing that this month
touches until the last week. **Treating it as urgent cost a day of machine time for
no schedule benefit.**

**Disposition: the 23 h partial is banked as evidence. The gate is scheduled for
week 3, alongside the work it actually gates.**

### 2. The running endurance test does not need the machine protected

A tick is counted late only when `lateness > tick_interval_s` — **a full 60 seconds**.
That is a generous threshold, and heavy memory work would have to starve the process
for a whole minute to trip it.

More decisively, the asymmetry runs the right way:

> **Load can only make the test harder to pass.** A pass under a hammered machine is a
> **stronger** result than a pass on an idle one. A failure under load tells us nothing
> we did not already accept losing — the 23 h partial is banked and the gate is not due
> until week 3.

**Disposition: the run continues, unprotected and opportunistic. Use the desktop for
anything. Pre-declared here, before the outcome: this run is being deliberately loaded,
so a resource or scheduling failure is environmental and must not be read as a product
defect. If it survives to 2026-08-18 00:09, the gate closes five weeks early for free.**

### 3. The cameras exist

`A-008`, `A-028` and `A-039` need a camera that can read a handwritten note and a
screen, an unknown person in frame, **a capture indicator the software can verify**, and
**a physical off that stops capture at source** (asserted by no frames arriving, not by
the software agreeing to stop).

Phones and tablets carry OS-level capture indicators; a lens cover is a physical off.
**The owner's inventory — phone, Linux laptop, iPhone, J3, old tablets, MacBook from
Thursday — plausibly satisfies all of it.** This was the largest blocked block in the
programme and it is likely not blocked.

**Disposition: Monday includes a hardware audit that turns "plausibly" into a list.
F4 starts this week rather than "when cameras exist".**

### 4. The alarm needs no hardware purchase — it needs a platform check

The previous plan put the alarm gate outside the month and named "buy alarm hardware" as
the way in. **That was wrong, and the owner corrected it.** The requirement is Jarvis-shaped
and entirely software: VESPER holds the schedule, notices the time, remembers being told to
wake the owner, speaks the wake-up, and escalates volume, noise and music across every
device it controls until acknowledged.

The two clauses that looked like hardware do not require any:

| Clause | What it asks | What satisfies it |
|---|---|---|
| `41.3` physical, ASR-independent acknowledgement | `RUNBOOK-ALARM` §1: *"Requires no speech, **no screen, no unlock**"* | A phone's **volume or power button**. A touchscreen tap does **not** qualify — the runbook rules out screen and unlock explicitly |
| `41.7` documented physical kill | A way to stop escalation when everything else fails | The runbook already answers it: *"power down the loudest node."* Any phone does this |
| `A-012` multimodal escalation | Fires on time, escalates across a device ladder, stops on acknowledgement, logs every step | The owner's always-on phone **is** a real device; the ladder needs more than one, and there are several |

**So nothing needs buying.** What it does need is one **platform-capability check**: can the
app capture a hardware-button press while the device is locked? That is `SPIKE-003`'s
question — per-platform privileged access — not a purchase. It is cheap, and it moves from
the night queue into **week 1** because a whole gate now depends on its answer.

**Disposition: the alarm gate moves inside the month. `SPIKE-003` is promoted to week 1.**
The one thing that genuinely cannot be compressed remains the runbook *validation*, which
requires the owner **genuinely asleep beforehand** — a wake-up procedure validated while
awake has not been validated. That is one night of ordinary sleep, not a purchase, and it
is scheduled rather than excluded.

### 5. The month is mostly software, so it is mostly reachable

Stages F0–F2 were built in roughly four days. What remains is F6, F7, F8 in full, the
hardware-gated remainder of F3/F4/F5, ten unrun spikes, and 41 unbuilt checks. At the
demonstrated rate the software is reachable. What is not reachable is named in
§*Outside the month*, and it is short.

## What this plan is honest about

It assumes the perception hardware works, and Monday's audit is what tests that
assumption rather than resting on it. It assumes F6 can be built against three real
nodes, which is now true. It does **not** assume the 27B model becomes hostable: the
bandwidth law in `QWEN38_27B_EVALUATION.md` §3 says a dense 27B reads ~14 GB per token
against 42 GB/s once it leaves VRAM, and no setting changes that division. If a stronger
local model is wanted, the property to shop for is **Mixture-of-Experts with a small
active-parameter count**, and `SPIKE-012` is where that gets decided on measurement.
