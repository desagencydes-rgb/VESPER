# Website brief — VESPER's public site

**For:** Codex, working alone, start to finish. **Owner's instruction:** build
it, publish it, and show the result. No back-and-forth; it has to be good on
the first delivery. **Read with:** `docs/SHOWROOM_BRIEF.md` (facts, status,
palette, assets) and `docs/INSTALL.md` (the install guide).

---

## The one job

**Make a visitor want to contribute before they reach the bottom of the page.**

VESPER is an open-source, persistent AI presence that lives on a Mac. It was
built by one person who has handed it to the world, and it is half finished
in honest, documented ways. The site has to make that feel like an invitation
— *here is something remarkable that is alive, and the missing pieces are
yours* — rather than a product page.

## What must be true (fixed)

1. **Facts come only from `docs/SHOWROOM_BRIEF.md`, `VESPER_OPEN_WORK.md` and
   `docs/INSTALL.md`.** Nothing aspirational is presented as built. Numbers
   are quoted with their date or re-measured with the commands in the brief.
2. **VESPER's own visual language.** The palette in SHOWROOM_BRIEF §6 (pitch
   `#03141f` ground, paper `#ffeae3`, accents ember / solar / blush / purple /
   gold / botanical / orange). Dark-first. Glass surfaces. Motion that settles
   rather than loops forever — the app's own rule is "play once, then settle".
3. **Real assets, not stock.** The wallpapers, videos, face reference and UI
   references listed in SHOWROOM_BRIEF §6. Label UI references as design
   references, not screenshots.
4. **Static and free to host.** GitHub Pages, published by a GitHub Actions
   workflow on push to `main`. No backend, no build step required to view
   (libraries from a CDN with pinned versions are fine).
5. **Fast and accessible.** Readable and navigable with JavaScript off and on a
   phone. Respect `prefers-reduced-motion` (the 3D scene becomes a still
   image). Under ~3 s to first meaningful paint on a normal connection; videos
   lazy-load, muted, `playsinline`.
6. **Scope of files.** Create everything under `site/`, plus one workflow in
   `.github/workflows/`. Change no other file. Do not run
   `docs/design/source/final.py`.

## The signature idea (the starting point; improve on it)

**The face is real data.** VESPER's face is a point cloud of 39,805 points,
generated by `docs/design/source/face_cloud.py` (it writes `face.bin`; the
format is in that script). Export it to a compact file under `site/` and render
it live in 3D (Three.js is the obvious choice): it breathes, it follows the
cursor with its gaze, it disperses into a field as the visitor scrolls and
re-forms — the app's own "dissolve" behaviour.

**The eleven modes are moods.** Each ambience mode (Home, Idle, Watch,
Listening, Thinking, Working, Speaking, Flow, Alert, Rest, Milestone — see
`docs/design/DESIGN-FOUNDATION.md` §7) has a wallpaper and an accent colour. Let
the visitor switch mode and have the whole page — the scene, the light, the
accent — change with it.

Everything else — layout, sections, transitions, typography, interactions — is
yours to invent. Surprise the owner.

## Pages

- **Home:** the living face, the thesis (keep the identity quote from the
  brief), what VESPER is in a few lines, the surfaces (island, home,
  showcase), the modes.
- **Status:** done / broken / unfinished / not solved, from SHOWROOM_BRIEF §4 —
  presented as a map of where help is needed, not a bug list.
- **Install:** `docs/INSTALL.md`, as a guided, step-by-step page.
- **Contribute:** the strongest page. Turn `CONTRIBUTING.md` and
  `VESPER_OPEN_WORK.md` §2–§4 into concrete "pick this up" cards (latency,
  Windows/Linux shell, non-blocking voice, model-composed scenes, the PENDING
  checks), each with what it is, why it matters, where to start, and a link to
  open an issue.
- **FAQ:** what VESPER is and isn't, privacy (keys stay local; egress classes),
  platforms, why it is open source now.

**Forms:** no backend, so use GitHub: "Open an issue" links with pre-filled
templates (add issue templates under `.github/ISSUE_TEMPLATE/` if useful — that
is the one other folder you may touch), and a `mailto:` fallback.

## Definition of done

- The workflow publishes the site; the GitHub Pages URL loads it.
- Every page checked at desktop and phone widths, with motion on and with
  reduced motion; no console errors; no broken links or images.
- The README gets one line linking to the site (the only README edit).
- `python3.13 tools/reference_lint.py` passes.
- A short final message to the owner: the URL, a screenshot of the home page,
  and anything that could not be done.
